## 7. The neighbour flag "indistinguishable"

The owner asked where the flag comes from in each case, and whether it should be there.
- **Method:**
  - the kitchen's saved coupling state (`dependencies.shared.coupling`) was copied from the
    instances read-only;
  - it was recomputed offline with SmartPI's own `coupling_estimator.py` of `qas` 7568df0
    (`indist/spk/`) using `indist/joint.py`, `door.py` and `reduced.py`;
  - in a counterfactual check, the 30-min windows were rebuilt from the recorder and fitted twice,
    once with the simulator's true model and once with SmartPI's (`indist/history_fetch.py`,
    `counterfactual.py`, `a_scan.py`, `a_scan_no_neighbour.py`).
- **Validation of the rebuild:** with the full true model it recovers the hall's `k` as 0.00395
  (true 0.004), and the true model leaves a residual of only ~0.0005 °C/min, the noise floor.

**How SmartPI sets the flag** (`smartpi/coupling_estimator.py`):
- **Routing:** a measurement window that contains any always-connected neighbour goes to the joint
  fit (`_submit`, 583–588). This applies to the hall too while the door is open, so the door's own
  path (589–595) is never reached.
- **The joint fit is all or nothing** (`_solve_joint_rows`, 620–634). It is refused when the
  regressors cannot be told apart, which is SmartPI's conditioning test: a condition number above
  30, or a variation below 0.5 °C. It is also refused when a coefficient's relative error exceeds
  0.15.
- **When it is refused,** every item in it is flagged (`is_indistinguishable`, 390–394).

| Case | Where the flag comes from | Counterfactual | Should it be there? |
|---|---|---|---|
| QD5, dining (always, held at its setpoint) | dining − outdoor and kitchen − outdoor correlate −0.998, condition number 6367: the conditioning test refuses the fit | the joint fit is refused **with the true model too** | **yes**: its exchange is a near-constant offset already in SmartPI's `b` (0.001127 against 0.001); a limit of the data |
| QD5, hall (door) | its own column barely correlates (−0.17 with dining, +0.22 with outdoor); it is flagged only because it shares the joint fit the dining makes fail | with the true model it is the best-determined coefficient (0.00397 ± 0.00009); with the dining folded into the loss it is separable with the true model (0.00369) and with SmartPI's (0.00373); SmartPI's own 90 windows refitted the same way give 0.00336 ± 0.00016, and through the door path 0.00325 | **no**: F7, the all-or-nothing joint fit |
| QD6, dining (always, stepping 18 / 22.5 °C) | the conditioning test passes (correlation −0.845, condition number 11.9); the error test refuses it: `k` 0.000835 ± 0.000370 (relative 0.44) | with the true model the same 109 windows give `k` 0.00298 ± 0.00004 and loss 0.00100; with SmartPI's `a`, `k` is 0.00207 (−31 %) | **not as a limit of the data**: it hides SmartPI's model error, F8 |

**Telling a hidden model error from the model** (the owner's question, 2026-10-20):

| Test | QD5 (instance 3) | QD6 (instance 1) |
|---|---|---|
| Residual of SmartPI's own model against the noise floor | 0.00094 °C/min, 1.8 × the floor (part of it the dining's exchange kept inside `b`) | 0.00302 °C/min, 6.2 × the floor |
| `a` that best fits the data (`a-scan-instance1.txt`) | — | 0.035, the truth: residual 0.00049; at SmartPI's 0.0249 the residual is 2.3 × larger |
| Fit of `a`, `b` and `k` together | — | `a` 0.03524, `b` 0.001006, `k` 0.00301: the truth |
| Fit of `a` and `b` without the neighbour's term, as SmartPI's model has none while `k` is unknown | `a` 0.0348, `b` 0.0011: right, since the dining is steady | `a` 0.0157, `b` 0.00046: biased low, the direction of SmartPI's learned values |

**The mechanism of F8.** SmartPI leaves an always-open neighbour with an unknown `k` out of its
model, and counts on its own `b` to hold that exchange (`dependency_model.py` 415–418).
- **When the neighbour is steady** (QD5), `b` holds it and nothing is lost.
- **When the neighbour moves on its own** (QD6), the left-out term biases `a` and `b` low. This is
  the omitted-variable bias the last row shows.
- **The joint fit then uses that `a`.** Each window's residual was built with the `a` of its time,
  which moved from 0.042 to 0.020, so the error test fails and the neighbour is flagged.
- **That is a loop that never corrects `a`.**

**Open point:** SmartPI's own saved windows are noisier than the rebuild with SmartPI's final
parameters (relative error 0.44 against 0.04 on instance 1). On instance 3 they give the hall 0.0033
against the rebuild's 0.0037. The likely causes are:
- `a` changing during the run (instance 1);
- the power SmartPI counts per cycle;
- the temperature it is fed;
- which windows it keeps (90 against 107 on instance 3).

**Proposed corrections in the plugin** (`decisions.log` 2026-10-20 15:05 and 2026-10-21 03:45):
1. **F7 — no longer all or nothing.** In `_solve_joint_rows`, fold only the always-columns that
   cannot be separated into the loss term, as SmartPI's `b` already holds them, and fit the rest.
   - On instance 3's own windows this gives the hall 0.00336 ± 0.00016, loss 0.00110.
   - A simpler alternative: while the always items cannot be separated, send door windows to the
     door path with SmartPI's `b` (0.00325).
2. **F8 — fit `a` in the joint fit.** In the joint fit of always-connected neighbours, fit `a`
   together with `b` and the `k` values, with the applied power as a regressor, as the zone fit
   does for `a`, `b` and `a_f`. Use that fit's `a` and `b` once it is separable and precise.
   - On QD6's windows this gives the truth: 0.0352, 0.00101, 0.00301.
   - Until then, reject single `a`/`b` measurements during which such a neighbour's difference
     changed by ≥ 0.5 °C.
3. **The reason instead of a single flag.** In `is_indistinguishable` and the neighbour's
   diagnostics (`dependency_model._status`, 1040–1067), each item reports one reason, together
   with the condition number, the relative error and the number of windows:

   | Reason | Meaning |
   |---|---|
   | `collinear` | the regressors cannot be told apart: a real limit of the data |
   | `uncertain` | separable, but the relative error is too large |
   | `implausible` | negative, or above the maximum |
   | `blocked` | its own column is separable, but another item made the fit fail |
   | `shared` | doors' common coefficient |

   Keep `indistinguishable` true only for `collinear` and `shared`. With this:
   - QD5's dining is `collinear`, and its hall `blocked`;
   - QD6's dining is `uncertain`.
4. **A residual test.** Compare the spread of the joint fit's residual with the noise that the
   sensor's resolution allows over a window. Far above it means the zone's model does not fit the
   data, and the diagnostics should say so instead of "uncertain".

**Missing tests in the fork's `tests/`:**
- door and always-open neighbours together: `test_smartpi_sim_neighbours.py` has n2 with a door
  only, and n3/n7 with always-open neighbours only, which is why F7 could not show;
- repeated always-neighbour steps, as in QD6, with `a` and `b` checked;
- estimator ticks with a wrong `a` must not end as `collinear`;
- `test_n3_coarse_sensor_publishes_nothing_doubtful` accepts the flag without checking `a`, the
  same leniency as QD6 (P14).
